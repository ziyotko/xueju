# 雪局小程序业务逻辑与交互逻辑梳理

## 本次修正点

### 1. 页面底部空白滚动
原因：多个页面同时使用了 `min-height: 100vh`、大额 `padding-bottom` 和 `tabbar-spacer`，短页面会被强行撑高，导致能滑出大段空白。

处理：
- 普通二级页面只保留 Home Indicator 安全区。
- Tab 页面单独预留自定义 TabBar 空间。
- `tabbar-spacer` 改为隐藏，不再额外撑高页面。
- 行程、消息、我的、评价、申请、审核、编辑资料、筛选、举报、雪友主页等页面统一收紧底部安全区。

### 2. 消息详情页导航栏遮挡
原因：聊天详情页使用了 `navigationStyle: custom`，但自定义头部没有完整处理刘海屏、胶囊按钮和状态栏高度，导致标题被遮挡。

处理：
- 聊天详情页恢复微信原生导航栏。
- 页面内头部改成行程摘要栏，不再承担导航栏职责。
- `onLoad` 根据当前行程动态设置原生导航标题。

### 3. 行程页 Tab 业务逻辑
之前问题：四个 Tab 的数据逻辑比较混，`我加入的 / 待确认 / 已结束` 都可能展示同一批数据。

处理：
- `我发起的`：展示自己发布的行程。
- `我加入的`：展示已通过的申请；演示环境没有通过申请时，用已成局示例兜底。
- `待确认`：只展示待审核申请。
- `已结束`：只展示历史行程，不再显示“即将出发”。
- 增加空状态，避免用户误以为页面坏了。

### 4. 行程详情页底部动作
之前问题：无论用户身份如何，都同时出现“申请列表 / 群聊 / 申请加入”，不符合真实业务。

处理：
- 发起人：展示“申请列表”和主按钮“进入群聊”。
- 已通过成员：展示“群聊”和主按钮“进入群聊”。
- 待审核用户：主按钮变为“待审核”，点击提示等待审核。
- 普通用户：展示“申请加入”。
- 已结束行程：主按钮可进入评价。

## 当前 MVP 推荐业务闭环

1. 首页发现行程
2. 进入行程详情
3. 普通用户申请加入
4. 发起人在申请列表中同意/拒绝
5. 同意后用户在“我的行程”里变为已加入
6. 用户进入局内群聊
7. 滑完后在“已结束行程”里提交评价
8. 评价进入个人主页沉淀信用

## 后续接后端时需要补的规则

1. 加入申请只能由行程发起人审核。
2. 满员后不允许继续申请。
3. 被拒绝后允许用户重新申请还是禁止，需要产品确认。
4. 局内聊天只允许发起人和已通过成员进入。
5. 滑后评价只能在行程结束后进行。
6. 同一个用户对同一个成员，同一个行程只能评价一次。
7. 举报后应进入后台待处理。
8. 个人资料、行程备注、聊天消息、评价内容都需要接入内容安全检测。
